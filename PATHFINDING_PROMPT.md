## 1. Threading model (do not break)
- Only the client thread touches the world. A `WalkCache` copies the world into a compact grid; a single daemon `Planner` thread reads ONLY the cache + snapshots (List<BlockPos> of targets, avoid set) and returns a `Plan` through an `AtomicReference`; the client thread `poll()`s it. `request()` returns false if a plan is already running (AtomicBoolean busy). Never block the client thread.

## 2. WalkCache (client thread, runs every tick)
- Grid 96x40x96 cells centered on the player (re-center when the player moves >16 horizontally or >8 vertically; copy over known cells). Two byte arrays: `data` (class) and `flags`.
- Fill ~12,000 cells per tick (hard cap 3 ms, check the clock every 512 cells), in a precomputed order sorted by distance from the center (counting sort on dx²+4dy²+dz²) so the nearest area is known first; cycle forever so changes are picked up.
- Classes: UNKNOWN, PASS (no collision), SOLID (collision top ≤ 1.0, includes STAIRS AS FULL BLOCKS and everything normal), LOW (top ≤ 0.6: slab/carpet/snow layer, walkable without jumping), TALL (top > 1.0: fence/wall/gate: not passable, not standable on top), FLUID (any non-empty fluid state).
- Flags: HAZARD (lava, fire, soul fire, magma block, cactus, sweet berry bush, wither rose, campfire, soul campfire, powder snow), SLOW (cobweb, soul sand, honey, mud).
- Queries: `passable` = PASS|LOW; `clear(x,y,z)` = feet+head passable; `standable(x,y,z)` = clear AND (floor below is SOLID|LOW, or the feet cell is LOW sitting on a non-air non-fluid block); `edge(x,y,z)` (orthogonal neighbour at this level is open air with no floor 1–2 below); `unsafe` (HAZARD in cell/floor/head or 4 neighbours); `slow`; `waterNear` (any FLUID in the 3x3x3 around); `tallNear` (TALL orthogonally adjacent at feet/head level).

## 3. Planner (worker thread)
- Input: start BlockPos (find a standable cell near the player: try same cell, ±1 y, 4 neighbours, y-2), list of target blocks, `keep` set (targets of the current leg), `avoid` set (cells where we recently got stuck).
- Search = Dijkstra over cell indices with a primitive PriorityQueue<Long> key (floatBits(cost)<<32 | idx). Arrays: dist[float], parent[int], kind[byte]. Cap 150,000 expansions, cost limit 160.
- Moves from each cell: 8 neighbours (diagonal cost 1.414, only if both side cells are `clear` → no corner clipping). If neighbour `standable` at same y → WALK. Else (orthogonal only): STEP_UP if `standable(n, y+1)` and head room above current (y+2 passable) cost +3.0 (a jump; slabs are WALK so slab routes win); else if the neighbour column is clear → DROP up to 3 (cost +0.3/block, stop if a non-passable cell is hit); optional GAP (flag `parkour`, default off): 1-block gap, landing 2 cells away at same y or one lower, +4.0.
- `relax`: skip `unsafe` cells entirely. Add costs: avoid +25, edge +1.0, slow +2.0, tallNear +0.8, waterNear +1.5.
- Targets are grouped into clusters (flood-fill, link distance 5). For each cluster scan standing cells within bbox±5 (y -4..+3), only cells with finite dist and not waterNear. Count targets within eye distance REACH=4.6 (eye = y+1.62). Pick per cluster the cell with max coverage (tie: lowest dist + 2 if on a ledge). Cluster score = covered / (cost + 6), ×1.3 if it contains a `keep` target (anti-flip-flop). Best score wins. Result leg targets = only those within reach from the chosen cell.
- Plan = up to 2 legs: leg 1 from the player; leg 2 searched from leg 1's stand cell over the remaining targets, so the next leg is ready the instant the first is cleared.
- Path extraction: walk `parent` back, then STRING-PULL: keep every non-WALK node exactly (takeoff/landing points); merge only runs of consecutive WALK cells, using `straight(a,b)` = same y and every cell under the line (and ±0.3 either side, 0.25-block steps) is `standable` and not `tallNear`. Output `Leg(List<Vec3> path, List<Move> moves, targets, stand, score, cost)` with `moves.get(i)` = how node i is reached (WALK/STEP_UP/DROP/GAP). Node pos = cell center x+0.5, y (feet cell), z+0.5.
- Keep a static `lastStats` string (legs, nodes expanded, ms, jumps/drops/gaps) for a debug command.

## 4. Controller (client thread, per tick) — plan lifecycle
- Every tick: `poll()` the planner; if a plan arrived and its first stand differs from the current leg, switch (`beginLeg`: start at the path node nearest the player, +1). Re-request a plan when: the target set changed (version counter), `planDirty`, or every 600 ms with no leg / 2 s with a leg; never more often than 250 ms.
- A leg is "alive" while any of its targets still exists and isn't blacklisted. When it dies, take `nextLeg` immediately.
- Blacklist targets for 15 s when: standing at the stand spot 1.5 s and they won't break; or stuck twice on the leg.
- LIVE VALIDATION every 150 ms: look at the next 6 path nodes in the live cache; if one is no longer `standable` → re-plan immediately (bypass the throttle).
- Stuck/avoid: when the follower reports STUCK, add the 3x3 cells around the player and the target node to `avoid` (30 s expiry) and re-plan.

## 5. Path follower (this is where most bugs were)
State: a `Cursor(points, moves, loop)` with index; `aim` = a camera controller (see §6).
Every tick, with `speed` = horizontal blocks/tick of the player's velocity:
1. NODE ADVANCE LOOP (up to 6 iterations; never advance only one node): for node `wp` with previous `prev`: `passed = segmentT(prev, wp, pos) >= 1` (projection along the segment). For WALK nodes reached = `hDist < max(1.2, speed*4)` (final node: `max(0.6, speed*2.5)`) OR passed. For STEP_UP/GAP nodes reached = (`hDist<0.9` and `player.y >= wp.y-0.6`) OR (`hDist<0.4` and onGround) OR (passed and `player.y >= wp.y-0.6`). Reason: at ~1 block/tick you fly over step nodes; if they stay the target they end up behind you, you turn around, overshoot, and run in circles. If passed a step node but a whole block too low and on ground → re-plan now.
2. STEERING = pure pursuit with a SPEED-SCALED look-ahead: `look = max(3, 2 + speed*10)` blocks along the path from the player's projection on the current segment (a short fixed look-ahead of 1.5 made it weave left/right at speed). If the next node is a step (within 2.5 blocks) aim directly at the node. If the straight line to the carrot is not `walkable` in the cache (same-y standable check) aim at the node instead.
3. When standing within 0.8 of the node: aim at the NEXT node, else along prev→node, else hold the current yaw (never atan2 toward a point under your feet: it flips and the camera spins).
4. Dead zone: if |yaw error| < 2° (and not a step) keep the current yaw (stops hunting on straight lines).
5. Keys: forward only if heading error < 75° (turn first on sharp corners), sprint only if error < 35°, not "careful", not near an edge. careful = final approach within 2.5 blocks, or a step ahead within `max(2.5, speed*8)`. Near an edge (`edge()` at the player cell or 1.2 blocks ahead): no sprint and pulse forward 2 of every 3 ticks. Coast (release forward) when within `speed*3+0.3` of the final node.
6. JUMPS come from the path's move types, not height guesses: GAP → jump when `toNode < 2.3 + speed` (sprinting); STEP_UP → jump when `toNode < max(1.3, speed*3)` and the node is ≥ 0.55 higher than the player's real y. Fallback: on `horizontalCollision` probe 0.5 and 0.9 blocks along the MOVEMENT direction (velocity, or direction to node if slow), never the camera yaw: collision top ≤ 1.01 with head room → jump; collision top > 1.01 (fence/wall/gate, 1.5 high) → NEVER jump, add the cell to `avoid` and re-plan immediately.
7. WATCHDOGS: (a) progress: if the distance to the current node hasn't improved by 0.3 within 25 ticks (and we're facing it, < 75°) → STUCK: avoid cells, pick a strafe side (the side whose neighbour cell is standable, else random), 6-tick recovery: back + strafe + hop with the yaw nudged 20° toward the strafe side, then re-plan. (b) anti-spin: accumulate |Δyaw| per tick while the node index is unchanged; > 540° → avoid the node + player cell, re-plan, and after 3 times blacklist the leg's targets. (c) warp-out: while trying to move, if the player stays within 3.5 blocks of an anchor for 6 s, or chases the same stand spot for 25 s, or is in water, or there is no leg for 3 s → run a configurable recovery command (cooldown 20 s, pause 1.2 s, then clear plan/avoid/anchors and re-plan).

## 6. Camera (HumanAim), runs per RENDERED FRAME, not per tick
- Per-tick rotation looks choppy at 20 Hz. Use a damped spring per axis: `acc = w²·err − 2·zeta·w·vel`, with w = 9..15 rad/s (random per target; pitch w×0.85), zeta 0.78..1.0 (random), speed cap parameter. For walking use cap 240°/s, stiffness 1.0 and force zeta ≥ 1.15 (no overshoot/sway). Output as whole mouse pixels: `step = (sens*0.6+0.2)³·8·0.15` degrees per pixel, carry the sub-pixel remainder, call `player.turn(px·e, py·e)` where e=(sens*0.6+0.2)³·8. Add `dt` clamp (1–33 ms). Target pitch ~6° while walking. Per-frame hook: call from `LevelRenderEvents.BEFORE_GIZMOS`.

## 8. Lessons to design around
- Stairs/fences/slabs have partial collision: treat stairs as full blocks (jump up), slabs as LOW (no jump), fences/walls/gates as TALL (impassable, never jump).
- At speed 400 everything is ~1 block/tick: arrival radii, jump trigger distances, look-ahead and slow-down distances must all scale with speed.
- Never aim at the node under your feet; never steer by `atan2` of a near-zero vector.
- Never use camera yaw to decide jumps; use movement direction or path move types.
- Throttle plan requests, but let validation/stuck events bypass the throttle.
- Mushroom/target memory: do not require "no targets known" for fallbacks; use "no reachable leg for N seconds".
